**현재 상태로 r003을 재시작해 shadow를 가동하는 것은 보류해야 합니다.** 주문 이후 체결과 복구는 개선됐지만, 사본 중복 생성·추가 매수 누락·장 마감 종료 경쟁이 남아 있습니다. 실제 주문을 바꾸는 경로는 확인되지 않았으나 shadow 결과의 신뢰성과 매매 루프 지연에 영향을 줍니다.

파일은 수정하지 않았습니다. 테스트는 코드를 대조했으며, 임시 파일을 생성하는 테스트 실행은 읽기 전용 요청에 따라 하지 않았습니다. 아래 경로는 `AutoBot/` 기준입니다.

4. **[심각도: 중간] 위치(`live_trading/r003_trade_live_execute.py:5920`, `:6394`; `live_trading/r026_exit_shadow.py:633`) - 장 마감 INCOMPLETE 처리가 스레드 실행 순서에 의존**

**가능한 회귀 위험과 확인 사항**

- `log()`는 `logger.info()` 호출입니다(`r003:1314`). `pos`·`quote_status`는 큐에 넣기 전에 복사하고, 작업 스레드가 사용하는 필드는 숫자·문자열·datetime입니다(`r026:594`). **이 경로의 얕은 복사를 확정적인 공유 객체 경쟁으로 보지는 않습니다.** 다만 공용 logging 핸들러의 느린 파일 쓰기는 다른 스레드의 로그 호출도 지연시킬 수 있습니다.
- **추정:** `trades_after()`는 초 단위 거래소 시각으로 엄격히 `>`를 비교합니다(`r025:258`). 10:00:01.100 주문 후 같은 초에 발생한 거래도 제외하므로 최대 다음 초까지 체결이 지연됩니다. 수신 시각만으로 바꾸면 지연 도착한 주문 전 거래를 잘못 체결할 수 있으므로, 같은 초 거래의 순서를 판별할 정책과 테스트가 필요합니다.
- **추정:** `halted`는 마지막 REST 상태에 의존합니다(`r025:351`). 실제 포지션 매도 후 REST 갱신이 끊긴 사본에서 마지막 상태가 정지이면, 이후 정상 거래가 들어와도 체결을 계속 막을 수 있습니다(`r026:429`, `:443`). 정지 상태의 유효기간·해제 정책을 검증해야 합니다.
- 저널의 INCOMPLETE 키를 복구에서 제외하는 것 자체는 정의된 종료 정책과 일치합니다(`r026:518`). 확인된 문제는 저널 복구가 아니라, **보류 매수분이 남은 정상 사본을 먼저 CLOSED로 만드는 경로**입니다.

**가동 판단**

반드시 고칠 것은 위 1~5번입니다. 비용 override를 사용하거나 결과를 성과 비교에 쓸 계획이면 6~7번도 먼저 수정해야 합니다. 특히 전량 주문 중 추가 매수, 실제 수량 감소 후 재매수, 진입 시각 누락, 장 마감 종료 경쟁, 느린 I/O 종료 테스트가 필요합니다.

수정 후 가동하면서 관찰할 것은 매매 루프 지연, 큐 적체·드롭, INCOMPLETE 비율, 동일 종목 사본 수, 같은 초 거래로 인한 체결 지연, 정지 해제 후 체결 재개입니다. 현재 드롭 수는 종료 때만 출력하므로(`r026:640`) 운용 중 주기적으로 확인할 수 있게 하는 편이 좋습니다.
