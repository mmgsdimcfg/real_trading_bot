**확인된 결함과 설계 누락 — 심각도순**

1. **[심각도: 높음] §1·§7.3 — 매도 대기 중에는 상위 손절 신호를 평가할 수 없다 — 실패 시나리오:** 100주 중 사다리 40주가 미체결인 상태에서 가격이 급락 손절선을 통과한다. 현재 메인 루프는 매도 pending이 있으면 `continue`하므로 신규 엔진에 도달하지 않는다(`live_trading/r003_trade_live_execute.py:6123`, `:6140`). 주문 함수도 진행 중 매도가 있으면 거절한다(`:5164`). 따라서 S7의 “취소 후 90주 손절”은 기존 경로 재사용만으로 작동하지 않는다. **수정 제안:** 미체결 중에도 고점·손절·우선순위를 평가하고, 주문 관리자에 취소·대체 의도를 전달하는 경로를 명시한다. 실제 제출은 취소 확인 후 한 곳에서만 수행한다.

2. **[심각도: 높음] §7.7 — 기존 영속 경로가 새 상태와 미체결을 보존하지 않는다 — 실패 시나리오:** 트레일 A 주문 접수 직후 재시작하면 단계가 초기화되어 A를 다시 주문하거나, 기존 주문과 중복 제출할 수 있다(발생 여부는 구현에 따른 추정). 현재 저장·복원은 필드 허용 목록 방식이므로 임의의 `ExitState` 필드를 붙여도 보존되지 않는다(`live_trading/r003_trade_live_execute.py:3107`, `:3197`, `:3564`). `pending_orders`도 생성 시 빈 사전이다(`:3516`). 최고가 재계산으로는 체결 수량·A 완료·취소 진행 상태를 복원할 수 없다. **수정 제안:** 직렬화·복원·버전 이전을 변경 범위에 포함하고, 시작 시 브로커의 당일 주문·체결·잔고를 대조한 후 주문을 허용한다. 주문 ID 하나 외에 잔여 수량, 취소 상태, 대체 주문 의도도 복구해야 한다.

3. **[심각도: 높음] §1·§12·§15 Q1 — shadow에서 기존 손절을 유지하는 실행 경로가 없다 — 실패 시나리오:** `AUTO_SELL_MODE="adaptive"`, `EXIT_ENGINE_MODE="shadow"`로 바꾸고 순손익이 -2.1%가 된다. 제안된 adaptive 목록에는 기존 `_s04_net_stop_loss`가 없고 새 엔진은 로그만 남기므로, 문서대로 단순 연결하면 기존 자동 손절이 사라진다(추정). 현재 stop_only는 별도 조건 목록으로 선택된다(`live_trading/r006_sell_conditions.py:1015`, `:1256`). 반대로 adaptive 값의 정규화·선택 분기를 추가하지 않으면 새 모드가 선택되지 않는다. **수정 제안:** 실제 주문은 기존 stop_only가 담당하고, 별도 가상 포지션 상태에서 adaptive를 평가하도록 계약을 확정한다. 예약 청산 역시 엔진 shadow 여부를 확인해야 한다. 현재 예약 청산의 차단 조건은 AUTO_SELL_MODE만 확인한다(`live_trading/r003_trade_live_execute.py:5276`).

4. **[심각도: 높음] §7.3 — 제시한 주문 방식이 기존 API 동작과 다르다 — 실패 시나리오:** KRX 사다리 목표 10,300원에 지정가를 요청해도 현재 `place_sell_order()`는 KRX를 항상 시장가로 제출한다. 5. **[심각도: 높음] §7.3·§10·S7 — 부분 체결 후 취소·재주문의 수량 및 단계 확정 규칙이 부족하다 — 실패 시나리오:** 40주 주문에서 10주 체결 후 30주를 취소한다. 현재 `refresh_pending_orders()`는 부분 체결 후 terminal이면 `_confirm_pending_sell()`을 호출하고 pending을 제거한다(`live_trading/r003_trade_live_execute.py:4213`). 기존 자동 정정 경로는 체결량 0주일 때만 실행된다(`:4244`). 이를 그대로 쓰면 남은 목표 30주나 상위 청산 의도가 유실될 수 있다(추정). **수정 제안:** 주문 접수·부분 체결·취소·거절·최종 체결을 구분하고, 누적 체결량의 증가분만 반영한다. 취소 확인 후 최신 실제 보유량에서 새 수량을 계산한다. S7의 마지막 상태는 90주 주문 제출 시 `CLOSING`, **90주 체결 확인 후** `CLOSED`여야 한다.

6. **[심각도: 높음] §7.4 — VI 손절 지정가가 청산 목적을 달성하지 못한다 — 실패 시나리오:** 손절선 9,800원, 예상체결가 9,600원인데 매도 지정가를 9,800원에 제출한다. 이 주문은 9,600원에 체결될 수 없어 하락 중 잔량이 남는다. 또한 현재 보관하는 상태 필드에는 예상체결가·상한가가 없다(`live_trading/r003_trade_live_execute.py:2202`, `:2220`). 틱 공백 뒤 단일가 체결을 확인하는 방식은 단일가 진행 중의 사전 감지 수단이 되지 못한다. **수정 제안:** VI·정지·상한가·예상체결가의 데이터 소스와 신선도를 명시하고, 손절선과 실제 주문 가격을 분리한다. FROZEN 중 강제 청산, 기존 주문 정정, 재개 직후 급락의 우선순위도 정한다.

7. **[심각도: 높음] §1·§7.6 — stale 가드가 SAFE 처리를 막고, 마감 청산과 데이터 단절 규칙이 충돌한다 — 실패 시나리오:** 틱과 REST가 25초 동안 끊긴다. 제안 목록의 첫 `_001`은 stale 가격이면 평가를 종료하므로 SAFE 진입 및 후속 처리가 막힌다(`live_trading/r006_sell_conditions.py:364`). 15:18에 단절이 60초를 넘으면 “강제 시장가”와 “새 주문 금지”도 충돌한다. **수정 제안:** 데이터 품질 판단을 엔진 앞단으로 옮기고, stale 가격을 사용하는 판단과 시간 기반 운영 판단을 분리한다. §15 Q13의 주문 금지를 유지하되 마감 청산과 충돌할 때의 우선순위를 명시한다.

8. **[심각도: 중간] §5 — 현재 손절의 확인 지연을 잘못 전제했다 — 실패 시나리오:** 순손익 -2.1%에서 2초 후 회복하는 경우, 현행 stop_only는 첫 관측에 주문하지만 새 설계는 3초 확인 때문에 주문하지 않는다. 문서는 이를 “현행 10초에서 3초로 단축”이라고 설명한다. 현재 적용되는 `_s04_net_stop_loss`에는 확인창이 없다(`live_trading/r006_sell_conditions.py:1234`, `:1258`). 10초는 normal 경로의 `HARD_STOP_CONFIRM_SECONDS`다(`live_trading/r001_define_config.py:787`). **수정 제안:** “현재 운용 대비 확인 지연 추가”로 효과를 바로잡고, 즉시 손절과 3초 확인을 별도 비교한다.

9. **[심각도: 중간] §4.1·§4.3·§7.1 — 단위와 호가 반올림이 허용폭 하한을 보장하지 않는다 — 실패 시나리오:** 진입가 10,000원에서 60원 하락은 gross 0.6%p지만 net으로는 **0.598620%p**다. `3×호가/진입가`도 비율이므로 %p 상수와 결합하려면 ×100이 필요하다. 고점을 실제 체결 호가에서 기록해도 계산 경계가 호가 사이에 놓이면 위쪽 올림 때문에 의도한 최소 가격 간격보다 일찍 발동할 수 있다. **수정 제안:** 내부 단위를 하나로 고정하고 net의 역변환식을 명시한다. `w1+2틱`도 같은 단위로 변환하며, 최종 가격 반올림 후 최소 3틱 및 A/B 간격을 다시 검증한다. `krx_tick_size()`의 구간 경계도 적용해야 한다(`live_trading/r008_strategy_v2.py:178`).

10. **[심각도: 중간] §4.3 — 동적 배율의 미정 구간과 동결 계산 순서가 있다 — 실패 시나리오:** RVOL=1.2는 `<1.0`과 `>=1.5` 사이여서 배율이 정의되지 않는다. 또 기본 w1=0.6, drop=0.3인 순간 AI가 w1을 0.7836으로 확대하면, 확대 후 기준으로 동결 여부를 검사할 때 `0.3<0.3918`이 되어 동결이 회피된다. S6이 기대하는 결과와 달라진다. **수정 제안:** RVOL 전 구간과 CTTR 조건 중첩의 우선순위를 정한다. 동결 판단에는 이전 확정 폭 또는 AI 적용 전 폭 중 무엇을 쓰는지 명시하고, 신고점 갱신→동결 해제→배율 계산→재동결 순서를 고정한다.

11. **[심각도: 중간] §2.1·§4.3·§6.2 — 틱 누락·예열 부족을 정상 수급으로 해석할 수 있다 — 실패 시나리오:** 매도 9,000주가 누락되고 매수 1,000주만 수신되면, 마지막 수신 시각은 신선하지만 CTTR은 극단적 매수 우위로 계산된다. 기존 틱 엔진은 누적거래량 증가와 체결량 차이로 누락을 감지한다(`live_trading/r009_tick_bars.py:143`). §10 스냅샷에는 이런 품질 상태가 없다. 매도체결량 0, 5분/10분 예열 미완료의 처리도 없다. **수정 제안:** 누락률·유효 창 길이·방향 미상 거래량을 전달한다. 누락 수량을 임의로 매수/매도에 배정하지 말고, 불완전한 CTTR·분배 신호로 폭을 확대하지 못하게 한다.

12. **[심각도: 중간] §2.1 — RVOL 분모의 원천 데이터 해석과 폴백이 불완전하다 — 실패 시나리오:** g001의 `raw_bar=1` 행만 선택하고 volume을 그대로 쓰면 분 거래량의 1/6을 분모로 사용해 RVOL이 약 6배가 된다. g001은 10초 실측 데이터가 아니라 분봉을 보간하고 거래량을 나눈 데이터다(`data_simulation/g001_data_collect_symbols_daily.py:10`, `:1052`, `:1063`). 신규 상장으로 슬롯 이력이 없으면 20일 일거래대금 폴백도 없으며, OBI 기본 off에서는 RVOL 없이 SURGE 확인 2개를 채울 수 없다. **수정 제안:** 원본 분봉 복원과 창 정렬을 명시하고, 상장 이력 부족·분모 0·거래정지일·시장별 세션 처리 규칙을 추가한다. 종목별 슬롯 RVOL은 가격대 정규화에 타당하지만, 거래대금 폴백은 장중 U자형 패턴을 제거하지 못한다.

**추정 회귀 위험과 추가 확정 사항 — 심각도순**

13. **[심각도: 중간] §6.3·§6.4 — AI 비율 변경과 폴백이 완료 단계의 누적 목표를 흔들 수 있다(추정) — 실패 시나리오:** AI가 1차 비율을 30%로 정해 30주 체결한 뒤 폴백으로 기본 누적 2차 70%를 적용하면, 다음 주문은 기본 30주가 아니라 40주가 된다. 단순히 모든 단계에 같은 부호의 변화량을 더하면서 합 1을 유지하는 방법도 정해져 있지 않다. **수정 제안:** 완료 단계의 목표·실제 체결은 고정하고, 변경은 남은 배분에만 적용한다. AI off/shadow가 폭뿐 아니라 비율·손절 강화에도 영향을 주지 않는지 검증한다. 하드 손절 래칫 원칙은 적절하지만 이 부분만으로 전체 청산 시점의 안전성이 보장되지는 않는다.

14. **[심각도: 중간] §6.4 — 지연 판정과 실행 중단은 다르며 캐시 유효성 계약이 부족하다(추정) — 실패 시나리오:** 추론이 영구 정지하거나 과거 스냅샷 결과가 늦게 도착한다. 별도 스레드로 메인 판단은 보호할 수 있지만, 작업이 계속 쌓이거나 오래된 결과가 최신 캐시를 덮을 수 있다. 현재 r011은 동기 추론과 분봉 단위 캐시이며, 청산용 50ms 타임아웃을 제공하지 않는다(`live_trading/r011_edge_ai.py:631`, `:697`, `:714`). **수정 제안:** 작업 수 제한, 요청 순번, 입력 스냅샷 시각, 늦은 결과 폐기 정책을 정한다. 확률 외에도 confidence·시각·latency의 NaN/무한대·음수·미래 시각을 거절한다. 현재 `valid_prob()`의 유한값 검사는 참고할 수 있다(`:562`).
