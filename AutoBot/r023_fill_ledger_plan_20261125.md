# r023 봇 보유 장부 - 체결 내역 기준으로 전환 (계획, 2026-11-25, Codex 검토 전)

## 배경
- 지금 r023 은 계좌 수량 차이로 귀속한다: 동기화 구간에 봇 주문이 있으면 증가 = 봇 매수, 감소 = 봇 매도 먼저.
- 한계(Codex A 검토 13차): 같은 구간의 봇 매도 체결 + 수동 매수가 상쇄되면 구분 불가, 장부 파일이 없으면 seed 가 과거 봇 종목 전량을 봇 몫으로,
  보류(A2) 중에는 증가분을 버리는 보수 규칙이라 봇 체결이 직접 보유로 잡힘, 매도 재주문이 기존 주문 수량을 그대로 씀.
- AUTO_SELL_SCOPE=bot_only 의 자동매도 수량이 이 장부를 쓰므로, 틀리면 직접 산 주식을 팔거나 봇 보유를 방치한다.

## 원칙 (실무)
- 봇 몫은 "봇이 낸 주문의 체결"로만 바뀐다. 계좌 수량은 상한(clamp)으로만 쓴다(사용자가 봇 몫을 직접 팔았으면 줄어든다).
- 모르는 것은 봇 몫으로 잡지 않는다(주문번호 없는 접수 불명, 조회 실패).

## 설계
1. 봇 주문 등록부(registry): `_order_cash` 가 접수 응답(rt_cd 0)을 받으면 주문번호를 등록 - {odno: {code, side, qty, date, at}}.
   모든 주문(신규, 분할 leg, 재주문, 매도)이 `_order_cash` 를 거치므로 빠짐이 없다. 취소 주문(order_rvsecncl)은 체결이 없어 등록하지 않는다.
2. 반영 기록(applied): {date: {odno: 반영한 체결 수량}} - 같은 체결을 두 번 더하지 않는다(재시작 포함, 장부와 같은 파일에 원자적으로 저장).
3. 체결 반영(apply_fills, 순수 함수): 당일 체결 조회(inquire_daily_ccld, 전 종목, 매수·매도 전체) 행 중 odno 가 등록부에 있는 것만:
   delta = tot_ccld_qty - applied[odno] (> 0 일 때) -> 매수면 bot += delta, 매도면 bot -= delta (0 미만 안 됨). applied 갱신.
4. 계좌 상한: 계좌 동기화 때 bot = min(bot, 계좌 수량), 계좌에서 사라진 종목은 장부에서 삭제. 계좌 증가는 봇 체결이 아니면 직접 보유.
5. 조회 주기: 등록부에 미완료 주문(반영 수량 < 주문 수량이고 당일)이 있을 때만, 최대 10초에 1번 + 대기 주문이 사라질 때 1번. 조회 실패 =
   변경 없음(다음에 다시). 모두 완료면 조회하지 않음.
6. 날짜: 등록부·applied 는 날짜별. 시작 시 전날(가장 최근 이전 거래일) 등록부에 미완료 주문이 있으면 그날 날짜로 체결 조회 1번(전날 r003 이
   멈춘 뒤 체결된 봇 주문 반영 - A2 의 "전날 보류는 첫 동기화 귀속" 대체). 7일 지난 기록은 정리.
7. A2 보류와의 관계: 주문번호가 있는 보류 주문은 등록부에 있으므로 체결이 정확히 반영 - "보류 중 증가분은 봇 몫 아님" 보수 규칙은 주문번호
   없는 보류(접수 불명)에만 남긴다(로그로 확인 요청).
8. seed(장부 파일 없음): 지금 규칙(최근 live_state 에 봇 매수 흔적이 있으면 전량 봇)은 과대 귀속 위험. 변경: 장부 파일이 없으면 등록부/체결로
   확인되는 당일 체결분만 봇, 나머지는 직접 보유 + 앱/로그 안내(이미 11-13 부터 장부 파일이 있어 실제로는 거의 안 탐).
   기존 장부 파일은 그대로 이어서 쓴다(첫 전환 때 기존 bot_qty 를 출발값으로).
9. 매도 재주문(_resubmit_repriced_sell_order): bot_only 면 재주문 수량 = min(남은 주문 수량, 그 시점 봇 수량).
10. dry-run: 등록부 사용 안 함(가짜 주문번호, 계좌 불변).

## 구현 결과 (v3, 2026-11-25, Codex 검토 1~19차 반영)

파일: `live_trading/r023_bot_holdings.py`(장부 순수 함수), `live_trading/r003_trade_live_execute.py`(조회·매도 연결), `tests/test_r023_fill_ledger.py`.
장부 파일 `bot_fill_ledger.json`(schema 2)은 r003 만 읽고 쓴다. `bot_holdings.json`(앱이 읽는 acct_qty / bot_qty)은 모양 그대로, 값만 이 장부에서 만든다.

장부가 가진 것
- `codes` 종목별 봇 몫 / 직접 몫(모르면 null), `registry` 봇 주문(주문일+번호), `applied` 주문별 반영한 누적 체결(직접 주문 포함).
- `debt` 다 빼지 못한 매도량, `pending_up` 계좌 대사로 직접 몫에 먼저 더한 양, `day_anchor` 그날 첫 조회 직전의 장부,
  `listed_through` / `listed_prev` 마지막으로 다 읽은 조회일과 그 전 조회일, `deducted` 번호 없는 봇 매도를 한 번만 뺀 기록.

규칙
1. 체결 반영: 봇 주문 체결은 봇 몫, 그 밖의 주문(직접) 체결은 직접 몫. 직접 매도는 확정된 직접 몫(직접 몫 - pending_up) 먼저, 나머지는 봇 몫.
   한 조회의 새 체결은 매도를 모두 먼저 반영한다(체결 시각이 없다). 다 빼지 못한 매도량은 debt 로 남겨 이후 매수(봇 매수 먼저)에서 갚는다.
2. 그날 상한: 조회마다 그날 체결 전체를 기준점에 "매도 먼저" 순서로 적용한 봇 몫을 계산해, 장부의 봇 몫이 더 크면 차이를 직접 몫으로 옮긴다.
   체결이 여러 조회에 어떤 순서로 나뉘어 보여도 봇 몫은 가능한 가장 작은 값 이하가 된다. 날짜가 바뀌면 전날 체결을 먼저 반영하고
   전날 기준점으로 한 번 더 적용한 뒤 오늘 기준점을 만든다.
3. 계좌 대사: 이번 차례에 조회가 계좌 읽기 뒤에 돌았고, 그 종목에 열린 주문·이번 체결 변화가 없고, 계좌의 금일 매수/매도 수량이 조회 합계와
   같을 때만 한다. 계좌가 더 많으면 직접 몫(pending_up 에도 기록), 적으면 직접 몫 먼저 줄인다. 봇 몫은 대사로 늘지 않는다.
   직접 몫을 모르는 종목은 같은 계좌 수량을 60초 간격으로 두 번 확인한 뒤 정한다.
4. 매도: bot_only 신규 매도와 재주문은 주문 직전에 계좌와 체결을 다시 읽는다. 수량 = min(요청, 계좌 보유, 봇 몫 - 미종결 봇 매도 - 응답 대기 중인
   매도 - 계좌엔 있고 조회엔 없는 오늘 매도). 체결 조회가 실패하면 그 매도는 하지 않는다.

감수한 동작 (봇 몫이 작아지는 쪽 - 그 수량은 자동 매도에서 빠지고 로그 `[BOT LEDGER  ]` 에 남는다)
- 봇 보유 종목을 같은 날 직접 샀다 팔면(왕복) 그 수량만큼 봇 몫이 직접 몫으로 넘어간다.
- 계좌가 먼저 보여 준 직접 매도가 조회에 다시 나오면 두 번 빠질 수 있다.
- 직접 몫을 모르는 동안의 직접 매도는 봇 몫에서 빠진다(r003 시작 뒤 1~2분, 새로 들어온 종목).

잔여 위험 (봇 몫이 클 수 있는 쪽 - 코드로 구분할 수 없음)
- 계좌와 체결 조회가 둘 다 아직 못 본 수 초: 봇 매도와 같은 수 초 안에 사용자가 그 종목을 직접 팔고 다시 사서 계좌 합계가 그대로인 경우.
- 전날 체결이 다음 날 첫 조회에도 없고 그 뒤에야 보이는 경우(수 시간 지연).
- 계좌 조회가 30초 넘게 계속 실패하면 마지막 계좌 값으로 매도를 진행한다(잔고 조회 장애 동안 손절이 막히지 않게).

  두 조회가 주문별로 엇갈려 늦는 경우). 권고는 "계좌의 오늘 매도 전량을 항상 빼기".
