# r028 진입 엔진 Codex 검토 (entry_engine_codex_review) - 2026-11-15

codex exec --sandbox read-only, 원문 그대로.

### 1. 확인된 결함

**1) 높음 — 워커의 로그 I/O가 실매매 메인 스레드를 대기시킬 수 있음**

- **위치:** `r003_trade_live_execute.py:2475, 1329`, `r028_entry_engine.py:951`
- **근거:** 워커에 전달하는 `log`는 실매매와 같은 `logger.info()`입니다. 이 로거는 동기 `FileHandler`, 콘솔, 종목별 파일 핸들러를 사용합니다(`r003:1255`, `1218`). 워커가 핸들러 잠금을 보유한 채 파일 쓰기·flush·콘솔 출력에서 지연되면 메인 스레드의 다음 로그도 기다립니다.
- **영향:** 별도 스레드라도 실매매 지연이 격리되지 않습니다. 라즈베리파이 저장장치나 출력 장치가 느릴 때 특히 문제가 됩니다.
- **수정 제안:** shadow 로그를 독립된 출력 경로로 보내거나, 메인과 워커 양쪽 모두 비동기 로그 큐를 사용하도록 분리하십시오. 큐 포화 시 메인 스레드를 기다리게 해서는 안 됩니다.

**2) 중간 — 확인 지연이 끝나기 전에 시간봉이 지표에 반영됨**

- **위치:** `r028_entry_engine.py:197, 200, 220, 693`
- **근거:** 다음 시간 구간의 틱이 도착하면 기존 시간봉을 즉시 닫고 `_on_bar()`로 전달합니다. `bar.avail`은 봉 종료＋5초로 설정하지만, 실제 지표 갱신은 그 시각까지 보류하지 않습니다.
- **재현 경로:** 09:03:00에 다음 봉 틱이 도착하면, 09:03:05부터 사용해야 할 직전 3분봉이 즉시 regime 지표에 반영됩니다. 이후 평가에는 `avail <= now` 검사가 없습니다.
- **영향:** 설정한 확인 지연을 위반한 조기 판단이 발생합니다. 확인 유예시간 내 직전 봉의 늦은 틱도 이미 닫힌 봉이라는 이유로 버려집니다.
- **수정 제안:** 미확정 시간봉을 별도로 유지하고 `end + delay` 이후에만 확정·지표 반영하십시오.

**3) 중간 — 고빈도 종목에서 틱마다 대형 리스트를 이동시킴**

- **위치:** `r028_entry_engine.py:272, 279`
- **근거:** 20,000개를 넘으면 매 틱 `_trim()`을 호출합니다. 2,400초 구간에 20,000개 이상이 유지되는 종목은 이후 오래된 틱이 생길 때마다 여섯 리스트의 앞부분을 삭제합니다. Python 리스트의 선두 삭제는 남은 원소를 이동시킵니다.
- **영향:** 보관 구간 길이는 제한하지만 연산량은 커집니다. 예를 들어 초당 100틱이면 약 24만 개 길이의 리스트 여섯 개를 반복 이동하여 CPU·GIL 경합이 발생할 수 있습니다.
- **수정 제안:** 선두 인덱스와 주기적 일괄 압축, 또는 시간 버킷 집계를 사용하십시오. 매 틱 물리적으로 선두를 삭제하지 마십시오.

**4) 중간 — 감시에서 제외된 종목도 오래된 가격으로 계속 판단함**

- **위치:** `r028_entry_engine.py:916, 932, 945`, `707`
- **근거:** `set_watch()`는 감시 집합만 교체합니다. 틱 공급은 현재 감시 종목에만 하지만, `engine.evaluate(now)`는 과거에 등록된 모든 `engine.codes`를 평가합니다.
- **영향:** 감시에서 빠진 종목의 후보가 남아 있으면 마지막 가격·지표로 `BUY`가 기록될 수 있습니다. 감시 제외와 함께 차단 사유도 사라지면 이전에 차단되던 후보가 통과할 수도 있습니다.
- **수정 제안:** 현재 감시 종목만 평가하고, 제외 시 후보를 종료하십시오. 재등록 시 누적 틱을 어떻게 처리할지도 정해야 합니다.

**5) 중간 — 실제 주문·체결과 shadow 후보의 지연 기록이 잘못 연결됨**

- **위치:** `r028_entry_engine.py:842, 853, 865, 944, 1032`
- **근거:** 연결 키가 종목 코드뿐입니다. 워커는 주문 큐를 먼저 처리한 뒤 틱을 읽습니다. 따라서 실제 submit을 기록한 직후 같은 주기의 `latency.start()`가 이를 `NO_FILL`로 종료할 수 있습니다. 주문 대기 중 새로운 후보가 생겨도 같은 덮어쓰기가 발생합니다. 이후 fill은 현재 열려 있는 다른 후보에 붙습니다.
- **추가 문제:** submit 연결 조건에는 `submit >= T1` 검사가 없어 미래 T1과 연결된 음수 지연도 허용합니다.
- **영향:** T0~T5 지연과 가격 변화 통계가 서로 다른 시도의 값으로 구성될 수 있습니다.
- **수정 제안:** shadow 후보 ID와 실제 주문 시도 ID를 분리하십시오. 제출된 주문 기록은 새 후보가 종료하지 못하게 하고, 명시적인 시간 순서 검증을 추가하십시오.

**6) 중간 — 전일 미완성 틱봉과 당일 틱이 섞임**

- **위치:** `r028_entry_engine.py:645, 651, 205`
- **근거:** 워밍업 후 tick series의 `forming`을 비우지 않습니다. tick series에는 날짜 전환 처리도 없습니다. 전일 마지막 60틱봉에 59틱이 남았다면 당일 첫 틱으로 봉을 완성합니다.
- **영향:** 서로 다른 세션의 가격·거래량으로 당일 트리거와 지표를 계산합니다. 기존 `r009_tick_bars.py:129`는 세션 전환 시 미완성 봉을 초기화합니다.
- **수정 제안:** 전일 확정봉으로 지표를 워밍업한 뒤 미완성 봉은 제거하십시오. SEQ/WIN 상태를 세션 간 유지할지도 명시해야 합니다.

**7) 중간 — AI 타임아웃이 실행 중인 추론을 중단하지 못함 — 선택 설정**

- **위치:** `r028_entry_engine.py:557, 558, 562`
- **근거:** 실행 중인 future에는 `cancel()`이 효력이 없습니다. 단일 워커가 멈춘 추론을 수행하는 동안 후속 작업은 제출·타임아웃·취소를 반복합니다. executor 종료 처리도 없습니다.
- **영향:** AI 기능이 계속 타임아웃하고 취소된 작업이 내부 큐에 쌓일 수 있습니다. 종료되지 않는 executor 작업은 프로세스 종료도 방해할 수 있습니다.
- **수정 제안:** 진행 중 요청을 하나로 제한하고 타임아웃 후 회로 차단을 적용하십시오. 강제 중단이 필요하면 별도 프로세스를 사용하십시오.
- **적용 범위:** 현재 기본값은 `off`이며 runner에는 predictor도 연결되지 않아 기본 shadow 경로에서는 발생하지 않습니다.

**8) 낮음 — 종료·날짜 전환 시 열린 지연 기록이 유실됨**

- **위치:** `r028_entry_engine.py:1004, 1038`
- **근거:** 종료 시 큐를 한 번 처리하지만 `latency.open`의 미완료 기록을 저장하지 않습니다. 큐 처리도 최대 500건 한 번이어서 남은 이벤트가 유실될 수 있습니다.
- **영향:** 마지막 미체결 시도와 미만료 후보가 jsonl에 남지 않습니다.
- **수정 제안:** 워커 종료 단계에서 열린 기록을 `STOP`/`DATE_CHANGE`로 확정 저장하고, 종료 시 큐 처리 정책을 명시하십시오.

### 2. 관찰 사항

- **실주문 호출 경로는 발견하지 못했습니다.** `OrderExecutor`는 상태 기계이며 shadow runner가 호출하지 않습니다.
- `global _ENTRY_SHADOW`는 `run()`의 첫 사용보다 앞에 있습니다. 해당 선언 위치 문제는 없습니다.
- submit/fill 훅은 `_entry_note()`에서 예외를 잡고 `put_nowait()`를 사용합니다. 주문 결과·수량·포지션 상태를 직접 변경하지 않습니다.
- 날짜 전환의 `close(timeout_s=0)`은 join하지 않습니다. 정상 종료에서는 entry shadow 때문에 **최대 3초** 추가 대기합니다. 생성 시 import·YAML 읽기는 메인 스레드에서 수행합니다.
- 감시 목록과 차단 사유는 tuple/dict로 복사되어 큐를 통과합니다. 엔진·봉·후보 상태는 워커에서 관리합니다. 다만 **로그 콜백과 로그 핸들러는 큐 밖에서 공유**합니다.
- `_rt` 등에는 이미 trim이 있어 단순한 하루 전체 무제한 누적은 아닙니다. 다만 틱 수의 절대 상한은 없고, 제외된 종목 상태와 `LatencyLogger.rows`는 계속 보관됩니다.
- `acml_vol`이 양수인 경우 동일·감소 값 제거는 구현되어 있습니다. 워밍업은 이 검사를 우회합니다.
- SEQ/WIN에는 기존 연구 구현과의 일치 테스트가 있습니다. 그 일치만으로 실시간 수신 순서·세션 경계의 정확성이 입증되지는 않습니다.
- 읽기 전용 정적 검토만 수행했습니다. 파일 수정 및 테스트 실행은 하지 않았습니다.

### 3. 누락 테스트

- 워커 로그 출력 지연 중 메인 매수·매도 경로의 진행 여부.
- 3분 경계 직후부터 확인 지연 만료까지의 regime 사용 금지 및 늦은 틱 반영.
- 실제 빈도의 다종목 장시간 입력에서 trim 연산량·메모리 상한.
- 후보 보유 종목의 감시 제외·재등록과 오래된 가격 사용 방지.
- submit 직후 새 후보, 주문 대기 중 새 후보, 큐 처리와 틱 공급 순서에 따른 지연 기록 연결.
- 전일 미완성 60/120틱봉, 전일 중복 틱, 당일 첫 틱 처리.
- 영구 정지 predictor의 반복 타임아웃·자원 정리·프로세스 종료.
- 날짜 전환·종료 시 열린 기록 저장과 500건 초과 큐 처리.
- `evaluate(now)`보다 미래에 수신된 틱·후보·regime이 판단에 사용되지 않는지 검증.
- r003 훅 실패·큐 포화 상황에서 기존 주문 처리 결과가 동일한지 검증.

### 4. 결론: "수정 후 가동"

직접 주문을 내는 결함은 발견하지 못했지만, **공유 동기 로그와 고빈도 trim 연산 때문에 실매매에 영향이 없다는 요구를 충족하지 못합니다.** 시간봉 확정과 지연 기록 연결 오류도 있어, 현재 shadow 결과를 그대로 판단·지연 검증 자료로 사용하기 어렵습니다.
